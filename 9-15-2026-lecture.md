## 1. Scheduling Problem, Queues & Metrics

### The Scheduling Context

The CPU scheduler executes inside the operating system kernel. It selects which runnable thread or process in the **Ready Queue** is dispatched to an available physical CPU core and decides how long that entity gets to execute.

```text
+------+  admitted   +-------+   dispatch   +---------+    exit    +------------+
| New  | ----------> | Ready | -----------> | Running | ---------> | Terminated |
+------+             +-------+              +---------+            +------------+
                        ^                      |   |
                        |     preempt / yield  |   | I/O wait
                        +----------------------+   v
                        |                      +---------+
                        +--------------------- | Waiting |
                             I/O complete      +---------+
```

The scheduler is invoked on four primary events:

1. **Block**: Process transitions from Running $\to$ Waiting (e.g., synchronous I/O request, lock acquisition).
2. **Exit**: Process transitions from Running $\to$ Terminated.
3. **Timer Interrupt**: Hardware timer signals time quantum expiration.
4. **Wake-up**: Process transitions from Waiting $\to$ Ready (e.g., disk I/O completed, network packet arrived).

### Scheduling Entity: Process vs. Thread

* **Early Unix (1970s–1980s)**: The process was the sole unit of scheduling because multi-threading did not yet exist.
* **Modern OS (Linux, Windows, macOS)**: The kernel schedules **kernel threads**. On Linux, processes and threads are represented internally by the same scheduling object (`struct task_struct`). In classical scheduling literature, the term "process" is used synonymously with "schedulable entity".

### The Core Scheduling Metrics

$$\text{Turnaround Time: } T_{\text{turnaround}} = T_{\text{completion}} - T_{\text{arrival}}$$

$$\text{Response Time: } T_{\text{response}} = T_{\text{first run}} - T_{\text{arrival}}$$

$$\text{Waiting Time: } T_{\text{waiting}} = T_{\text{turnaround}} - T_{\text{burst}} \quad (\text{for pure CPU-bound workloads without I/O})$$

$$\text{Throughput} = \frac{\text{Completed Processes}}{\text{Time Period}}$$

```text
Arrival (t=0)             First Run (t=4)                           Completion (t=12)
   |                             |                                         |
   v                             v                                         v
   +-----------------------------+--------------------+--------------------+
   |           WAITING           |      RUNNING       |      WAITING       |  RUNNING  |
   +-----------------------------+--------------------+--------------------+
   0                             4                    7                    10          12
   [<------ Response (4) ------->]
   [<---------------------------- Turnaround (12) ------------------------------------>]
   Total CPU Burst = (7 - 4) + (12 - 10) = 5
   Total Waiting Time = 12 - 5 = 7 (composed of intervals [0..4] and [7..10])
```

### Preemptive vs. Non-Preemptive Execution

| Architectural Trait | Non-Preemptive Scheduling | Preemptive Scheduling |
| --- | --- | --- |
| **CPU Relinquishment** | Process holds CPU until it voluntarily terminates or blocks. | Kernel forcibly revokes CPU via timer or event interrupts. |
| **Timer Hardware** | Not strictly required. | **Mandatory** hardware timer interrupt. |
| **Response & Fairness** | Poor; interactive jobs get trapped behind long compute jobs. | High; CPU is interleaved rapidly across tasks. |
| **Context Switches** | Minimal overhead (switches occur only at natural boundaries). | Higher switch frequency; incurs cache and TLB costs. |
| **Historical Precedent** | Early Windows (3.x), classic Mac OS (System 7). | Linux, POSIX/Unix, modern Windows, macOS. |

### Standard Workload & Tie-Breaking Conventions

The following standard workload (`basic.txt`) is used throughout this lecture to evaluate all policies under identical arrival conditions:

| Process | Arrival Time ($T_A$) | CPU Burst Length ($T_B$) | Priority ($1 = \text{highest}$) |
| --- | --- | --- | --- |
| **P1** | 0 | 8 | 4 (lowest) |
| **P2** | 1 | 4 | 2 |
| **P3** | 2 | 2 | 3 |
| **P4** | 3 | 1 | 1 (highest) |

**Course & Exam Conventions**:

1. **Completion at Quantum Expiry**: If a process finishes its burst at the exact moment its quantum expires, it is marked terminated and exits; the next job starts immediately.
2. **Simultaneous Arrival and Quantum Expiration**: If process $A$ expires its slice at the same instant process $B$ arrives, the newly arrived process $B$ enqueues **before** expired process $A$.
3. **Preempted Queue Placement**: A preempted job is appended to the back of its queue with a fresh quantum.
4. **Context Switch Cost**: Assumed to be $0$ abstract time units unless explicitly stated.
5. **Tie-Breaking Rule**: FCFS breaks ties by arrival time / input order. SJF and Priority break ties by arrival time / input order. SRTF preempts only if the new process is **strictly shorter** (`remaining < current.remaining`).

## 2. Non-Preemptive Scheduling: FCFS & SJF

### First-Come, First-Served (FCFS / FIFO)

Runs processes strictly in the order of their arrival until completion. The ready queue is a standard First-In, First-Out (FIFO) queue.

```text
FCFS Execution Timeline:
+--------------------------------+----------------+--------+----+
|               P1               |       P2       |   P3   | P4 |
+--------------------------------+----------------+--------+----+
0                                8                12       14   15
```

| Process | Arrival | Burst | Completion | Turnaround ($T_C - T_A$) | Waiting ($T_{\text{turn}} - T_B$) | Response ($T_{\text{first}} - T_A$) |
| --- | --- | --- | --- | --- | --- | --- |
| **P1** | 0 | 8 | 8 | $8 - 0 = 8$ | $8 - 8 = 0$ | $0 - 0 = 0$ |
| **P2** | 1 | 4 | 12 | $12 - 1 = 11$ | $11 - 4 = 7$ | $8 - 1 = 7$ |
| **P3** | 2 | 2 | 14 | $14 - 2 = 12$ | $12 - 2 = 10$ | $12 - 2 = 10$ |
| **P4** | 3 | 1 | 15 | $15 - 3 = 12$ | $12 - 1 = 11$ | $14 - 3 = 11$ |
| **Average** | — | — | — | **10.75** | **7.00** | **7.00** |

> **Note**: For all non-preemptive workloads without I/O, **Waiting Time equals Response Time** because every process runs continuously from its first dispatch to completion.

**The Convoy Effect**: Short CPU-bound or I/O-bound processes become stuck in the queue behind a single long compute-heavy job. For example, if a 20-unit job is followed by four 1-unit jobs, average wait climbs to 16.2 units.

---

### Shortest Job First (SJF / SPN)

When the CPU becomes free, the scheduler chooses the ready process with the shortest CPU burst. It is non-preemptive; once a process receives the CPU, it runs to completion.

```text
SJF Execution Timeline:
+--------------------------------+----+--------+----------------+
|               P1               | P4 |   P3   |       P2       |
+--------------------------------+----+--------+----------------+
0                                8    9        11               15
```

* At $t=0$: Only P1 has arrived. P1 runs despite having an 8-unit burst.
* At $t=8$: P1 completes. Ready queue contains P2 (burst 4), P3 (burst 2), and P4 (burst 1). Shortest job is P4.
* At $t=9$: P4 completes. Ready queue contains P2 (burst 4) and P3 (burst 2). Shortest job is P3.
* At $t=11$: P3 completes. P2 runs to completion at $t=15$.

| Process | Arrival | Burst | Completion | Turnaround | Waiting | Response |
| --- | --- | --- | --- | --- | --- | --- |
| **P1** | 0 | 8 | 8 | 8 | 0 | 0 |
| **P2** | 1 | 4 | 15 | 14 | 10 | 10 |
| **P3** | 2 | 2 | 11 | 9 | 7 | 7 |
| **P4** | 3 | 1 | 9 | 6 | 5 | 5 |
| **Average** | — | — | — | **9.25** | **5.50** | **5.50** |

**Optimality Condition**: SJF is provably optimal for minimizing average waiting time **if and only if all jobs arrive simultaneously at $t=0$**. When arrivals are staggered, non-preemption prevents SJF from intercepting long jobs that started earlier.

## 3. Preemptive Scheduling: SRTF, Priority & Round Robin

### Shortest Remaining Time First (SRTF)

The preemptive variant of SJF. The scheduler evaluates remaining burst time at every process arrival and completion. If an incoming job's remaining time is strictly less than the currently running job's remaining time, the running job is preempted and returned to the ready queue.

```text
SRTF Execution Timeline:
+----+----+--------+----+----------------+--------------------------------+
| P1 | P2 |   P3   | P4 |       P2       |               P1               |
+----+----+--------+----+----------------+--------------------------------+
0    1    2        4    5                8                                15
     ^    ^
     |    +-- Preemption: P3 (rem 2) preempts P2 (rem 3)
     +------- Preemption: P2 (rem 4) preempts P1 (rem 7)
```

* $t=0$: P1 begins (rem: 8).
* $t=1$: P2 arrives (rem: 4). P1 has 7 remaining. $4 < 7 \implies$ P2 preempts P1.
* $t=2$: P3 arrives (rem: 2). P2 has 3 remaining. $2 < 3 \implies$ P3 preempts P2.
* $t=3$: P4 arrives (rem: 1). P3 has 1 remaining. Tie condition ($1 = 1$); strictly shorter rule means **no preemption**.
* $t=4$: P3 completes. Ready: P4 (rem 1), P2 (rem 3), P1 (rem 7). Scheduler dispatches P4.
* $t=5$: P4 completes. Scheduler dispatches P2 (rem 3).
* $t=8$: P2 completes. Scheduler dispatches P1 (rem 7).
* $t=15$: P1 completes.

| Process | Arrival | Burst | Completion | Turnaround | Waiting | Response |
| --- | --- | --- | --- | --- | --- | --- |
| **P1** | 0 | 8 | 15 | 15 | 7 | 0 |
| **P2** | 1 | 4 | 8 | 7 | 3 | 0 |
| **P3** | 2 | 2 | 4 | 2 | 0 | 0 |
| **P4** | 3 | 1 | 5 | 2 | 1 | 1 |
| **Average** | — | — | — | **6.50** | **2.75** | **0.25** |

### The Burst-Time Problem & Exponential Smoothing

In real operating systems, future CPU burst lengths are unknown. The kernel cannot natively inspect code to predict when a thread will next issue an I/O system call. To approximate SJF/SRTF, kernels predict future burst duration $\tau_{n+1}$ using **exponential averaging** of historical bursts:

$$\tau_{n+1} = \alpha \cdot t_n + (1 - \alpha) \cdot \tau_n$$

* $t_n$: Actual observed duration of the $n$-th burst.
* $\tau_n$: Predicted duration of the $n$-th burst.
* $\alpha$: Weighting factor ($0 \le \alpha \le 1$).
* $\alpha = 0 \implies \tau_{n+1} = \tau_n$ (historical predictions never update).
* $\alpha = 1 \implies \tau_{n+1} = t_n$ (only the most recent burst is used).
* Common default: $\alpha = 0.5$ balances recent behavior against historical baseline.

### Priority Scheduling

Each process is assigned an integer priority value (by system convention here: **lower number = higher priority; 1 is highest**). Can be preemptive or non-preemptive.

#### Preemptive Priority Trace

```text
Preemptive Priority Execution Timeline:
+----+--------+----+--------+--------+--------------------------------+
| P1 |   P2   | P4 |   P2   |   P3   |               P1               |
+----+--------+----+--------+--------+--------------------------------+
0    1        3    4        6        8                                15
```

* $t=1$: P2 (Priority 2) arrives and preempts P1 (Priority 4).
* $t=2$: P3 (Priority 3) arrives; P2 is running and has higher priority ($2 < 3$). P2 continues.
* $t=3$: P4 (Priority 1) arrives and preempts P2 (Priority 2).
* $t=4$: P4 completes. Ready: P2 (Prio 2), P3 (Prio 3), P1 (Prio 4). P2 resumes.
* $t=6$: P2 completes. P3 runs to completion at $t=8$.
* $t=8$: P1 resumes and runs to completion at $t=15$.

| Process | Arrival | Burst | Priority | Completion | Turnaround | Waiting | Response |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **P1** | 0 | 8 | 4 | 15 | 15 | 7 | 0 |
| **P2** | 1 | 4 | 2 | 6 | 5 | 1 | 0 |
| **P3** | 2 | 2 | 3 | 8 | 6 | 4 | 4 |
| **P4** | 3 | 1 | 1 | 4 | 1 | 0 | 0 |
| **Average** | — | — | — | — | **6.75** | **3.00** | **1.00** |

**Starvation & Aging**:

* **Starvation**: Low-priority processes can wait indefinitely if a continuous stream of higher-priority processes enters the ready queue.
* **Aging Solution**: Gradually increase process priority as it spends time waiting in the ready queue:

$$\text{Priority}_{\text{effective}} = \text{Priority}_{\text{base}} - \left\lfloor \frac{\text{Time Spent Waiting}}{N} \right\rfloor$$

Every $N$ time units spent waiting decrements the priority number by 1, guaranteeing that any starved process eventually achieves top priority.

### Round Robin (RR)

Designed for time-sharing systems. Processes execute in FIFO order for a bounded time slice called a **time quantum ($q$)**. When the quantum expires, the running process is preempted and placed at the back of the ready queue.

```text
Round Robin (q = 2) Execution Timeline:
+----+----+----+----+----+----+----------------+
| P1 | P2 | P3 | P1 | P4 | P2 |       P1       |
+----+----+----+----+----+----+----------------+
0    2    4    6    8    9    11               15
```

* $t=0$: P1 runs.
* $t=2$: P1's quantum expires (6 left). At the exact same instant, P3 arrives. **Convention 2 applies**: P3 enqueues ahead of expired P1. Ready queue: `[P2, P3, P1]`. P2 is dispatched.
* $t=3$: P4 arrives. Ready queue: `[P3, P1, P4]`.
* $t=4$: P2's quantum expires (2 left). Ready queue: `[P3, P1, P4, P2]`. P3 is dispatched.
* $t=6$: P3 completes its 2-unit burst. Ready queue: `[P1, P4, P2]`. P1 is dispatched.
* $t=8$: P1's quantum expires (4 left). Ready queue: `[P4, P2, P1]`. P4 is dispatched.
* $t=9$: P4 completes its 1-unit burst early. P2 is dispatched.
* $t=11$: P2 completes its remaining 2 units. P1 runs its remaining 4 units to completion at $t=15$.

| Process | Arrival | Burst | Completion | Turnaround | Waiting | Response |
| --- | --- | --- | --- | --- | --- | --- |
| **P1** | 0 | 8 | 15 | 15 | 7 | 0 |
| **P2** | 1 | 4 | 11 | 10 | 6 | 1 |
| **P3** | 2 | 2 | 6 | 4 | 2 | 2 |
| **P4** | 3 | 1 | 9 | 6 | 5 | 5 |
| **Average** | — | — | — | **8.75** | **5.00** | **2.00** |

**Worst-Case Wait Bound**: In a system with $n$ active processes and quantum $q$, no process waits longer than $(n - 1) \cdot q$ time units for its next turn.

### Tuning the Time Quantum ($q$) vs. Context Switch Cost ($c$)

$$\text{Switch Overhead Ratio} = \frac{c}{q + c}$$

```text
[ Quantum q (Useful Work) ] [ c (Switch) ] [ Quantum q (Useful Work) ] [ c (Switch) ]
```

* **$q \to \infty$**: Preemptions never fire; Round Robin degrades directly into **FCFS**.
* **$q \to 0$**: Near-instantaneous response time, but the CPU spends the vast majority of its cycles executing kernel context switches rather than user instructions (processor thrashing).
* **Rule of Thumb**: Set $q$ such that roughly 80% of typical CPU bursts are shorter than $q$, while keeping switch overhead below 1–5% of the time slice.

## 4. Multi-Level Queue (MLQ) & Multi-Level Feedback Queue (MLFQ)

### Multi-Level Queue (MLQ)

Processes are permanently classified at creation into distinct priority queues (e.g., Q0: System, Q1: Interactive, Q2: Batch). Each individual queue maintains its own internal scheduling policy (e.g., Round Robin with varying quanta).

* **Limitation**: Static classification causes starvation for lower queues if higher queues remain continuously occupied. Furthermore, a process whose behavior changes (e.g., an interactive application that transitions into a long encoding phase) cannot adapt its priority.

---

### Multi-Level Feedback Queue (MLFQ)

MLFQ dynamically adjusts process priority based on observed CPU and I/O behavior. It seeks to optimize turnaround time (like SJF/SRTF) without advance knowledge of burst lengths, while maintaining low response times for interactive jobs.

```text
               +--------------------------------------+
[ New Task ] ->| Q0: Highest Priority (Round Robin, q) |
               +--------------------------------------+
                                   | (allotment exhausted)
                                   v
               +--------------------------------------+
               | Q1: Medium Priority  (Round Robin, 2q)|
               +--------------------------------------+
                                   | (allotment exhausted)
                                   v
               +--------------------------------------+
               | Q2: Lowest Priority  (Round Robin, 4q)|
               +--------------------------------------+
```

### The Five MLFQ Rules

1. **Rule 1**: If $\text{Priority}(A) > \text{Priority}(B)$, process $A$ runs ($B$ waits).
2. **Rule 2**: If $\text{Priority}(A) == \text{Priority}(B)$, processes $A$ and $B$ run in Round Robin using the time quantum of that queue.
3. **Rule 3**: When a job enters the system, it is placed at the highest priority queue (Q0).
4. **Rule 4 (Cumulative Allotment)**: Once a job uses up its cumulative time allotment at a given level (regardless of how many times it voluntarily yields for I/O), its priority is reduced by one level (demoted down one queue).
5. **Rule 5 (Priority Boost)**: After a fixed time period $S$, move **all** jobs in the system to the topmost queue (Q0) and reset their allotment counters.

### Standard MLFQ Environment Parameters (Homework 2 / Exam Baseline)

* **Queues**: 3 Priority Queues (`Q0`, `Q1`, `Q2`), where `Q0` is the highest priority.
* **Time Quanta**: $\text{Q0} = 2$, $\text{Q1} = 4$, $\text{Q2} = 8$.
* **Allotment**: Allotment at level $k$ equals the quantum of level $k$ ($\text{Allotment}_k = q_k$), tracked cumulatively.
* **Priority Boost**: Periodic boost interval $S = 20$.

### MLFQ Execution Walkthrough (Standard Workload)

```text
MLFQ Execution Timeline across Queues:
Q0: [ P1 ] [ P2 ] [ P3 ] [ P4 ]
    0    2      4      6      7
Q1:                            [      P1      ] [  P2  ]
                               7              11       13
Q2:                                                     [  P1  ]
                                                        13     15
```

* $t=0$: P1 enters Q0, runs for its 2-unit quantum.
* $t=2$: P1 exhausts its 2-unit allotment at Q0; demoted to Q1. Simultaneously, P3 arrives. Ready at Q0: `[P2, P3]`. P2 runs.
* $t=3$: P4 arrives at Q0.
* $t=4$: P2 exhausts its 2-unit allotment at Q0; demoted to Q1. P3 runs in Q0.
* $t=6$: P3 completes its 2-unit burst entirely inside Q0. P4 runs in Q0.
* $t=7$: P4 completes its 1-unit burst inside Q0. Q0 is now completely empty.
* $t=7$: Scheduler examines Q1, which contains `[P1, P2]`. P1 runs for its Q1 allotment of 4 units.
* $t=11$: P1 exhausts its Q1 allotment; demoted to Q2. P2 runs in Q1.
* $t=13$: P2 completes its remaining 2 units in Q1. Q0 and Q1 are empty.
* $t=13$: Scheduler drops to Q2. P1 runs its remaining 2 units to completion at $t=15$.

| Process | Arrival | Burst | Completion | Turnaround | Waiting | Response | Final Queue Level |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **P1** | 0 | 8 | 15 | 15 | 7 | 0 | Q2 |
| **P2** | 1 | 4 | 13 | 12 | 8 | 1 | Q1 |
| **P3** | 2 | 2 | 6 | 4 | 2 | 2 | Q0 |
| **P4** | 3 | 1 | 7 | 4 | 3 | 3 | Q0 |
| **Average** | — | — | — | **8.75** | **5.00** | **1.50** | — |

### The Gaming Problem: Cumulative Allotment vs. Full-Quantum Rule

* **The Flawed Rule (Single-Slice Full Quantum)**: If a rule demotes a job only when it runs a single continuous burst equal to the quantum, a malicious or CPU-bound job can game the scheduler by running for 99% of its quantum and then issuing a dummy I/O operation (e.g., writing 1 byte to a pipe). Because it relinquished the CPU before quantum expiration, its allotment is reset, allowing it to remain permanently in Q0 and monopolize 99% of CPU capacity.
* **The Modern Defense (Rule 4 Cumulative Accounting)**: The OS tracks cumulative CPU time spent at a level. Once a process consumes a total duration equal to the allotment—regardless of how many times it yielded for I/O—it is demoted.

## 5. Linux Scheduling: CFS & EEVDF

### Completely Fair Scheduler (CFS)

From Linux 2.6.23 (2007) through Linux 6.5 (2023), the standard default scheduler for normal tasks (`SCHED_OTHER` / `SCHED_NORMAL`) was the **Completely Fair Scheduler (CFS)**. (Linux 6.6+ transitioned to the Earliest Eligible Virtual Deadline First [EEVDF] scheduler, maintaining similar proportional-share foundations).

CFS implements **proportional-share scheduling** using an abstract metric known as **virtual runtime (`vruntime`)**:

$$\Delta \text{vruntime} = \Delta \text{runtime} \times \frac{\text{Weight}_{\text{nice } 0}}{\text{Weight}_{\text{task}}}$$

* As a task executes, its physical runtime is scaled inversely by its assigned weight and added to its `vruntime`.
* CFS maintains runnable tasks in a time-ordered **Red-Black Tree** keyed on `vruntime`.
* The scheduler always picks the task with the **smallest `vruntime`** (the leftmost node in the tree) to run next.

```text
              [Red-Black Tree: Ordered by vruntime]
                            ( vruntime = 14 )
                               /          \
                     ( vruntime = 8 )   ( vruntime = 22 )
                         /
     ==> [ Leftmost: vruntime = 4 ]  <-- SCHEDULER PICKS THIS TASK NEXT
```

### The `nice` Value and Weight Table

Process priority is adjusted using nice values ranging from **$-20$ (highest priority)** to **$+19$ (lowest priority)**, with a default of **$0$**.

| `nice` Value | Kernel Weight (`sched_prio_to_weight`) | CPU Share vs. `nice 0` Task |
| --- | --- | --- |
| **-20** | 88761 | ~86.7 : 1 |
| **-5** | 3121 | ~3.05 : 1 |
| **0** (default) | **1024** | **1 : 1** |
| **5** | 335 | 1 : 3.06 |
| **10** | 110 | 1 : 9.31 |
| **19** | **15** | **1 : 68.3** |

Every increment of 1 in nice value reduces CPU allocation by approximately **$1.25\times$** (a geometric progression providing consistent relative proportions regardless of base nice value).

### Dynamic Time Slices: Latency Target & Granularity

Unlike classical Round Robin, CFS does not use a fixed static quantum. Time slices are calculated dynamically based on the number of runnable tasks ($n$) and the kernel's **Target Latency** ($L$, default 24 ms):

$$\text{Time Slice} = \frac{\text{Target Latency } (L)}{n}$$

* If 2 runnable tasks: $\text{Slice} = 24 \text{ ms} / 2 = 12 \text{ ms}$ each.
* If 3 runnable tasks: $\text{Slice} = 24 \text{ ms} / 3 = 8 \text{ ms}$ each.
* **Minimum Granularity ($G$, default 10 ms on FIU systems)**: To prevent context switch thrashing when $n$ becomes very large, time slices are never allowed to fall below $G$. If $L / n < G$, the slice is clamped to $G$, and the overall scheduling period stretches to $n \times G$.

### Practical Linux Inspection & Management Commands

```bash
# Launch a CPU-intensive background job at lowest priority (nice 19)
nice -n 19 ./video_encoder &

# Adjust the nice level of an already running process by PID
renice -n 5 -p 4242

# View real-time scheduling priority (NI) and CPU usage
top -p 4242

# Inspect voluntary vs non-voluntary context switches
grep ctxt /proc/4242/status
# voluntary_ctxt_switches:    process yielded voluntarily (e.g. blocking I/O)
# nonvoluntary_ctxt_switches: kernel forcibly preempted process (time slice expired)
```
