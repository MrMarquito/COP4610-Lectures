## 2. The Protection Problem & Dual-Mode Execution

### Why Not Run Bare Metal?
Running directly on hardware leads to poor maintainability, zero isolation, and catastrophic safety hazards: a single crash or malicious instruction takes down the entire machine.

### Hardware Enforcement: Dual Mode
Modern CPUs enforce boundaries using a hardware-level **Mode Bit**:
- **Kernel Mode (`Mode Bit = 0`)**: Full execution privileges, direct hardware access, unrestricted memory mapping, modification of control registers.
- **User Mode (`Mode Bit = 1`)**: Restricted privileges; direct hardware access and privileged instructions are blocked.

### Crossing the Boundary (User $\to$ Kernel)
User applications enter Kernel Mode exclusively via **Traps**:
1. **System Call (Syscall)**: Programmatic request initiated by software (e.g., `read()`, `fork()`).
2. **Hardware Interrupt**: Asynchronous external event (e.g., timer slice expiration, disk controller I/O ready).
3. **Exception / Fault**: Program runtime error or trap condition (e.g., division by zero, page fault).

## 3. Part 1: The Process Abstraction (What & Why)

### Definition
A **process** is an execution stream in the context of an isolated execution state:
$$\text{Process} = \text{Program Counter (PC)} + \text{Registers} + \text{Address Space (Memory State)}$$

### Virtualizing the CPU
The OS transforms a finite number of physical CPU cores into an illusion of near-infinite dedicated cores:
- **Time-sharing**: Rapidly swapping running processes via timer interrupts and context switches.
- **Space-partitioning**: Dividing resources spatially. While common in RAM (address spaces) and large GPUs (e.g., NVIDIA MIG), pure space-partitioning fails on general CPUs because 1,000 tasks cannot map to 1,000 physical cores.

## 4. Part 2: The Process API (How)

### Core System Call Categories

| Category | Typical Syscalls (C Wrappers) | Purpose |
| :--- | :--- | :--- |
| **Process Control** | `fork()`, `exec()`, `wait()`, `exit()`, `getpid()` | Lifecycle and execution state management |
| **File Operations** | `open()`, `read()`, `write()`, `close()`, `lseek()` | Manipulating byte streams and storage |
| **Device Control** | `ioctl()`, `mmap()`, `read()`, `write()` | Interacting with peripherals ("everything is a file") |
| **Information** | `getpid()`, `time()`, `sleep()`, `alarm()` | Querying/setting kernel-managed metadata |
| **Communication** | `pipe()`, `socket()`, `shmget()`, `send()`, `recv()` | Inter-Process Communication (IPC) |

## 5. Under the Hood: The 7-Step Syscall Journey

When a user program calls a library wrapper like `read(fd, buf, count)`:

```text
+-------------------------------------------------------------+
| USER SPACE                                                  |
|  1. User Program calls read(...)                            |
|       |                                                     |
|  2. libc loads %rax = SYS_read, %rdi, %rsi, %rdx            |
|       |                                                     |
|  3. CPU runs `syscall` trap instruction                     |
+-------|-----------------------------------------------------+
        |  TRAP: CPU flips Mode Bit (1 -> 0)
+-------v-----------------------------------------------------+
| KERNEL SPACE                                                |
|  4. Dispatch: lookup sys_call_table[%rax]                   |
|       |                                                     |
|  5. Validate: check pointers, bounds, permissions           |
|       |                                                     |
|  6. Execute: sys_read() talks to storage/hardware           |
+-------|-----------------------------------------------------+
        |  RETURN-FROM-TRAP: CPU flips Mode Bit (0 -> 1)
+-------v-----------------------------------------------------+
| USER SPACE                                                  |
|  7. Return to User: bytes placed in %rax; app resumes       |
+-------------------------------------------------------------+
```

### Breakdown of the 7 Steps

1. **Invoke System Call**: The user program initiates the request by invoking the C wrapper function (e.g., `read()`).
2. **Prepare Registers**: The C library (`libc`) places the syscall number into the CPU register (`%rax = SYS_read`) and loads the function arguments into registers (`%rdi = fd`, `%rsi = buf`, `%rdx = count`).
3. **Syscall Instruction**: The CPU executes the `syscall` trap instruction, crossing the protection boundary.
4. **Dispatch**: The hardware switches to Kernel Mode (`Mode Bit = 0`) and transfers execution to the predefined kernel entry point, which indexes the system call vector table.
5. **Validate**: The kernel verifies every parameter before proceeding (e.g., checking if the file descriptor is valid, buffer belongs to user space, memory is writable, and permissions are met).
6. **Execute**: The kernel handler (`sys_read`) carries out the privileged hardware operation.
7. **Return to User**: The kernel voluntarily initiates a return-from-trap instruction, restoring user registers, placing the return byte count into `%rax`, resetting the Mode Bit to `1`, and resuming user program execution.

## 6. Hands-On Verification: Inspecting Syscalls with `strace`

Even a minimal C program incurs dozens of setup system calls before printing:

```c
// hello.c
#include <stdio.h>

int main() {
    printf("Hello!\n");
    return 0;
}
Bash
$gcc hello.c -o hello$ strace ./hello
Key Syscalls Observed:

execve("./hello", ...): Kernel loads and prepares the new program.

brk() / mmap(): Kernel sets up virtual memory, heaps, and shared libraries (libc.so.6).

write(1, "Hello!\n", 7): Standard C printf flushes to file descriptor 1 (stdout).

exit_group(0): Process terminates cleanly and reports return code to OS.
