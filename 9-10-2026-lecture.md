## 1. Motivation: Why Not Just Processes?

When building high-concurrency software (such as a web server handling incoming requests, client I/O, database queries, and disk logging simultaneously), splitting tasks across separate processes incurs steep performance penalties.

```text
Multi-Process Model:
Main Process ---> fork() ---> Child (Client A) [Separate Address Space]
             ---> fork() ---> Child (Client B) [Separate Address Space]
             ---> fork() ---> Child (Logging)  [Separate Address Space]
```

### The Three Process Bottlenecks

1. **Expensive Creation**: `fork()` must allocate an address space and copy page tables entry-by-entry. Even with Copy-on-Write (COW), each child's first write triggers a page fault trap so the kernel can duplicate that physical frame.

2. **Expensive Communication**: Processes are isolated by default. Sharing data requires Inter-Process Communication (IPC) via pipes or message queues, which forces data to cross kernel space twice (2 syscalls, 2 copies per message).

3. **Expensive Context Switches**: Swapping between processes requires repointing the CPU's page-table base register. This flushes or invalidates entries in the Translation Lookaside Buffer (TLB), leaving the new process with a "cold TLB" that forces slow memory walks for early address translations.

```text
Root Cause: Tasks in the same program often share the same data and state.
Forcing them into isolated address spaces pays for protection they never requested.
```

### Memory Footprint: Processes vs. Threads

In benchmark tests running 20 idle workers on Linux, page-table memory overhead scales drastically with processes compared to threads:

| Workers ($N$) | Process Model (Page Table Memory) | Thread Model (Page Table Memory) | Overhead Difference |
| --- | --- | --- | --- |
| **1** | 92 kB | 52 kB | ~1.8x |
| **10** | 448 kB | 88 kB | ~5.1x |
| **20** | 844 kB (21 address spaces) | 128 kB (1 address space) | ~6.6x |
| **40** | 1484 kB | 212 kB | ~7.0x |

Each additional process adds 30–40 kB of page-table overhead, whereas each additional thread adds only about 4 kB (one page for the stack allocation).

## 2. What is a Thread?

A **process** is an execution container holding resources and an address space. A **thread** is an independent execution stream executing within that container.

$$\text{Process} = \text{Address Space} + \text{OS Resources} + \text{One or More Threads}$$

$$\text{Thread} = \text{Program Counter (PC)} + \text{Stack Pointer (SP)} + \text{Registers} + \text{Thread ID (TID)}$$

```text
+----------------------------------------------------------------------+
| Process: ONE Address Space                                           |
|  [ Code ]               [ Data (Globals) ]           [ Heap ]        |
|  (Shared by all)        (Shared by all)              (Shared by all) |
|                                                                      |
|  +----------------+    +----------------+    +----------------+      |
|  | Thread 1 Stack |    | Thread 2 Stack |    | Thread 3 Stack |      |
|  +----------------+    +----------------+    +----------------+      |
+----------------------------------------------------------------------+
| OS Resources (Process-Wide): PID, Open File Table, CWD, Credentials  |
+----------------------------------------------------------------------+
| Thread 1 (TCB)         | Thread 2 (TCB)         | Thread 3 (TCB)     |
| - PC, SP, Registers    | - PC, SP, Registers    | - PC, SP, Registers|
| - TID                  | - TID                  | - TID              |
+------------------------+------------------------+--------------------+
```

### Analogy: House vs. Residents

* **Process = House**: Has a street address (address space), shared living spaces/appliances (heap, globals, open files), and an owner (user credentials).
* **Threads = Residents**: Live in the same house and share common areas, but each has their own bedroom (private stack).
* **Where the Analogy Breaks**: Bedroom doors have no locks. Hardware and kernel memory protections do not isolate stacks within the same address space; any thread can read or modify another thread's stack if it obtains a pointer to it.

### Shared vs. Private State

| Memory Region / State | Shared or Private? | Reason / Implementation Detail |
| --- | --- | --- |
| **Code / Instructions** | **Shared** | All threads run functions defined in the same binary. |
| **Data (Globals / Static)** | **Shared** | Reside at fixed virtual addresses accessible across the program. |
| **Heap (`malloc` / `free`)** | **Shared** | Dynamically allocated memory can be referenced by any valid pointer. |
| **File Descriptors & CWD** | **Shared** | Tracked at the process level in kernel process control blocks. |
| **Registers (`PC`, `SP`)** | **Private** | Represents distinct CPU execution state; saved in the Thread Control Block (TCB). |
| **Stack** | **Private*** | Holds local variables and call frames; private **by convention**, not hardware isolation. |
| **Thread ID (`pthread_t`)** | **Private** | The unique handle used by the runtime and kernel to distinguish execution flows. |

### Stack Anatomy and Memory Layout

In single-threaded programs, the stack starts at high memory and grows downward toward the heap. In multi-threaded programs:

* The main thread retains the original stack setup by `execve`.
* Worker thread stacks are allocated as fixed-size blocks (default 8 MB on Linux) mapped via `mmap`.
* A 4 kB unmapped **guard page** sits directly below each worker stack. If a stack overflows, accessing the guard page immediately triggers a hardware page fault (segmentation fault) instead of silently corrupting neighboring thread memory.

## 3. Performance: Creation & Context Switching

### Why Thread Creation is Lightweight

Before executing user instructions, `fork()` and `pthread_create()` complete different initialization steps:

| Action Step | `fork()` (New Process) | `pthread_create()` (New Thread) |
| --- | --- | --- |
| **Address Space** | Allocates a brand-new virtual address space. | Reuses the caller's existing address space. |
| **Page Tables** | Duplicates entries entry-by-entry. | Allocates one or two pages for the new stack mapping. |
| **File Descriptors** | Duplicates file table references. | Untouched (shared automatically). |
| **Kernel Structure** | Allocates a complete Process Control Block (PCB). | Allocates a smaller Thread Control Block (TCB). |
| **Execution State** | Duplicates caller registers; returns twice ($0$ and child PID). | Sets registers to start directly at target function. |

**Benchmarked Creation Cost (1,000 rounds, wall-clock time)**:

* On 32-core AlmaLinux (`ocelot`): `fork() + wait()` took **140–144 µs**, while `pthread_create() + pthread_join()` took **28–30 µs** (~**4.7x–4.9x faster**).
* On a 2-core Linux VM: threads proved **3.2x–3.5x faster**.

### Thread vs. Process Context Switch

```text
Process Context Switch:
[Save Registers to PCB] -> [Swap Page-Table Base Register] -> [TLB Flushed / Tagged] -> [Load New PCB]
                                                                        ^
                                                      Expensive hardware performance hit

Thread Context Switch (Same Process):
[Save Registers to TCB] --------------------------------------------------------------> [Load New TCB]
                     Page-table base unchanged; TLB entries remain fully valid
```

## 4. The Price of Sharing: Race Conditions

Because threads share an address space, inter-thread communication takes a single memory write instead of a kernel system call. However, uncoordinated writes lead to race conditions.

### The Disassembly of `count++`

At the C language level, `count++` looks like a single atomic operation. In assembly, it executes as three separate instructions:

1. **Load**: Read value from shared memory into a register (`movq count(%rip), %rax`).
2. **Modify**: Increment register value (`addq $1, %rax`).
3. **Store**: Write register back to shared memory (`movq %rax, count(%rip)`).

### Problematic Interleaving (Lost Updates)

When two threads attempt to increment a shared counter ($count = 5$) concurrently:

```text
Time   Thread 1                        Thread 2                        Shared Value
 |     1. Load count into reg1 (5)                                     count = 5
 |     2. Add 1 to reg1 (6)                                            count = 5
 |     -- PREEMPTED / PARALLEL --      1. Load count into reg2 (5)     count = 5
 |                                     2. Add 1 to reg2 (6)            count = 5
 |                                     3. Store reg2 into count (6)    count = 6
 v     3. Store reg1 into count (6)                                    count = 6
```

**Result**: Two increments executed, but `count` advanced by only 1. One update was silently overwritten and lost.

### Core Concurrency Terminology

* **Race Condition**: A flaw where system behavior depends on the non-deterministic relative timing or interleaving of threads.
* **Critical Section**: A block of code that accesses shared mutable state and must not be concurrently executed by more than one thread.
* **Mutual Exclusion**: The synchronization property guaranteeing that only one thread accesses a critical section at any given time.
* **No Fault Isolation**: In a multi-process architecture, a segmentation fault in a worker kills only that child process. In a multi-threaded architecture, an illegal memory access in one thread terminates the **entire process** and all peer threads.

## 5. Threading Models: User vs. Kernel

Threads can be scheduled at user level or kernel level:

| Dimension | Many-to-One ($N:1$, User-Level) | One-to-One ($1:1$, Kernel-Level) | Many-to-Many ($M:N$, Hybrid) |
| --- | --- | --- | --- |
| **Architecture** | Many user threads map to 1 kernel task. | 1 user thread maps to 1 kernel task. | $M$ user threads map to $N$ kernel tasks. |
| **Switch Mechanism** | Handled in user space by runtime library (stack swap). | Handled by OS scheduler inside kernel. | Handled jointly by runtime and kernel. |
| **Multi-Core Parallelism** | **No** (Kernel sees only 1 runnable task). | **Yes** (Runs threads across multiple cores). | **Yes** (Kernel tasks spread across cores). |
| **Blocking Syscalls** | **Severe**: One thread calling `read()` blocks the entire process. | **Safe**: Only the calling thread blocks; others keep running. | **Safe**: Runtime shifts unblocked user threads to free kernel tasks. |
| **Primary Examples** | Early "Green Threads" libraries. | **Linux (NPTL)**, Windows, macOS. | Go goroutines, Java Virtual Threads. |

### Why Modern Operating Systems Choose 1:1

Early OS architectures explored $M:N$ threading, but operating systems like Linux, FreeBSD, and Solaris ultimately converged on the **1:1 model**:

1. Multi-core hardware became universal, requiring true kernel-level parallel scheduling.
2. Blocking system calls are frequent, and preventing whole-process stalls under $N:1$ models required overly complex non-blocking wrappers.
3. Kernel thread primitives (such as Linux `clone()` and `futex`) became efficient, rendering kernel-level switches fast enough to eliminate the user-space speed advantage.

## 6. Part 2: POSIX Thread (pthread) API

The POSIX threads standard (`pthreads`) follows the lifecycle conventions of the process API with specific signature differences:

| Process Primitive | POSIX Thread Primitive | Conceptual Difference |
| --- | --- | --- |
| `fork()` | `pthread_create()` | `fork()` clones execution at the callsite; `pthread_create()` starts execution at a designated function pointer. |
| `wait()` / `waitpid()` | `pthread_join()` | `pthread_join()` targets a specific thread handle and reclaims its stack and TCB. |
| `exit()` | `pthread_exit()` | `exit()` terminates the entire process; `pthread_exit()` terminates only the calling thread. |
| `pid_t` | `pthread_t` | `pthread_t` is an opaque library handle, distinct from the Linux kernel TID (`gettid()`). |
| Returns `-1`, sets `errno` | Returns error code directly | pthread functions return error numbers directly ($0$ on success) and do not set `errno` (use `strerror(err)`). |

### Core Function Prototypes

```c
#include <pthread.h>

// Spawns a new thread executing start_routine(arg)
int pthread_create(pthread_t *thread, 
                   const pthread_attr_t *attr,
                   void *(*start_routine)(void *), 
                   void *arg);

// Blocks until target thread terminates; captures return value and reclaims resources
int pthread_join(pthread_t thread, void **retval);

// Terminates the calling thread without killing the process
void pthread_exit(void *retval);
```

### Pattern 1: Passing Arguments and Collecting Results

To pass parameters and collect data cleanly without casting tricks, pack thread inputs and outputs into dedicated `struct` instances allocated per thread:

```c
// hello_threads.c
#include <stdio.h>
#include <pthread.h>

#define N 4

struct worker_arg {
    int id;
    long result;
};

void *worker(void *p) {
    struct worker_arg *arg = (struct worker_arg *)p;
    printf("Worker %d executing\n", arg->id);
    arg->result = arg->id * 100;
    return NULL; // Return via struct rather than pointer casting
}

int main(void) {
    pthread_t tid[N];
    struct worker_arg args[N];

    for (int i = 0; i < N; i++) {
        args[i].id = i;
        pthread_create(&tid[i], NULL, worker, &args[i]);
    }

    for (int i = 0; i < N; i++) {
        pthread_join(tid[i], NULL);
        printf("Worker %d returned %ld\n", i, args[i].result);
    }
    return 0;
}
```

### Pattern 2: Returning Values via the Heap

If returning an allocated value directly from `start_routine`, allocate from the heap—never the stack:

```c
void *compute(void *arg) {
    int *res = malloc(sizeof(int)); // Heap survives thread termination
    *res = 42;
    return (void *)res;             // Equivalent to: pthread_exit(res);
}

int main(void) {
    pthread_t tid;
    void *ret;
    pthread_create(&tid, NULL, compute, NULL);
    pthread_join(tid, &ret);        // Captures pointer returned by thread
    
    printf("Result: %d\n", *(int *)ret);
    free(ret);                      // Caller owns cleanup
    return 0;
}
```

### Compilation

Threaded applications must be linked against the POSIX threads runtime using the `-pthread` flag:

```bash
gcc -Wall -o my_threads my_threads.c -pthread
```

*Note*: Compiling without `-pthread` on older `glibc` environments (pre-2.34) results in linker errors (`undefined reference to pthread_create`). Always supply `-pthread` for portability.

## 7. Common Pitfalls & Practical Fixes

### Pitfall 1: Forgetting to Join (Premature Process Exit)

* **Symptom**: Worker thread output never appears, or terminates halfway through execution.
* **Root Cause**: The `main()` thread reached `return 0` or called `exit()`, destroying the process address space and terminating all child threads instantly.
* **Fix**: Block the main thread with `pthread_join(tid, NULL)` until the worker finishes, or terminate the main thread using `pthread_exit(NULL)` (which keeps workers running until the last thread completes).

### Pitfall 2: Passing the Address of a Shared Loop Variable

```c
// BUGGY CODE
for (int i = 0; i < 5; i++) {
    pthread_create(&tid[i], NULL, worker, &i); // PASSING &i IS BROKEN
}
```

* **Symptom**: Threads print unexpected, skipped, or duplicated IDs (e.g., workers receive `2, 2, 2, 5, 5`).
* **Root Cause**: All worker threads receive a pointer to the single memory address of `i`. By the time the thread runs, the main thread's loop has already incremented `i`.
* **Fix Option A (Per-Thread Array)**:

```c
int ids[5];
for (int i = 0; i < 5; i++) {
    ids[i] = i;
    pthread_create(&tid[i], NULL, worker, &ids[i]);
}
```

* **Fix Option B (Cast by Value via `intptr_t`)**:

```c
#include <stdint.h>
// Caller:
pthread_create(&tid[i], NULL, worker, (void *)(intptr_t)i);

// Worker:
void *worker(void *arg) {
    int id = (intptr_t)arg; // Unpack value directly without memory lookup
    ...
}
```

### Pitfall 3: Returning Pointers to Deallocated Stack Frames

```c
// BUGGY CODE
void *worker(void *arg) {
    int local_val = 42;
    return &local_val; // BUG: Stack frame reclaimed on function exit
}
```

* **Symptom**: Dereferencing the returned pointer in `main` outputs garbage values, causes intermittent crashes, or triggers undefined behavior.
* **Root Cause**: When a thread terminates, its call stack is invalidated. Any pointer referencing local variables inside that frame becomes a dangling pointer.
* **Fix**: Store return values in heap memory (`malloc()`) or write results directly into memory provided by the caller (such as an argument struct).

### Pitfall 4: Memory Leak from Unjoined / Undetached Threads

* **Symptom**: Process memory footprint continuously climbs over time as threads are spawned and finish.
* **Root Cause**: When a thread terminates without being joined, its 8 MB stack and kernel TCB remain allocated in "zombie" state so that `pthread_join` can still read its exit value.
* **Fix**: Always call `pthread_join(tid, NULL)` to reclaim memory. If the return value is not needed and the creator will not wait, detach the thread at creation:

```c
pthread_detach(tid); // Stack automatically deallocated immediately upon termination
```

## 8. Diagnostic & Inspection Quick-Reference

When debugging multi-threaded binaries on Linux, use process status tools to view underlying kernel tasks:

```bash
# Compile and launch program in background
gcc -Wall -o sleepers sleepers.c -pthread
./sleepers 4 &

# Check PID, Number of Light-Weight Processes (NLWP), and command name
ps -o pid,nlwp,comm -p <PID>

# Inspect all kernel task directories assigned to this process
ls /proc/<PID>/task/
```

* **`NLWP`**: Indicates the exact number of active kernel-level execution contexts. A program running a main thread plus 4 workers reports an `NLWP` count of `5`.
* **`/proc/<PID>/task/`**: Contains subdirectories named by the Kernel Thread ID (`gettid()`) for each running thread.
